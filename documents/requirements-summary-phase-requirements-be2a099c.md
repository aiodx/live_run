# Requirements Summary — Arithmetic Feedback Screen

---

## Functional requirements

What the solution must do, numbered, each testable, each tied to who needs it.

**Number display**

FR-01 — The screen must display exactly two numbers at all times when in the ready state. *(User: needs to know what to add.)*
- Pass: Two numbers are visible on screen before the Answer button is pressed.
- Fail: Fewer or more than two numbers are shown; numbers are absent.
- Test case: Correct answer path, Wrong answer path.

FR-02 — The two numbers must be generated by the application, not entered by the user. *(User: sees a problem to solve, not a blank to fill.)*
- Pass: Numbers appear without any user action; no input field exists for the operands.
- Fail: The user is required to type either operand.
- Test case: Correct answer path, Wrong answer path.

FR-03 — The two numbers must be whole numbers (integers). *(User: can type a plain number without confusion about decimals.)*
- Pass: Both displayed numbers are integers with no decimal point.
- Fail: Either number contains a decimal point or fractional part.
- Test case: Correct answer path, Wrong answer path.

FR-04 — The correct answer is the arithmetic sum of the two displayed numbers (addition). *(User: is practising addition.)*
- Pass: Evaluation compares user input to operand-one plus operand-two.
- Fail: Any other arithmetic operation is used; the comparison uses a value other than the sum.
- Test case: Correct answer path, No wrong-condition feedback.

**Answer field**

FR-05 — The screen must provide exactly one text input field for the user to type their answer. *(User: has a clear place to write their response.)*
- Pass: One input field is present and accepts typed characters.
- Fail: No field exists; more than one field exists; the field is read-only.
- Test case: Correct answer path, Wrong answer path, Empty field.

FR-06 — The answer field must be empty (cleared) at the start of each interaction cycle. *(User: does not see a previous answer carried over.)*
- Pass: The field contains no text when a new problem is presented.
- Fail: A previous answer remains in the field when a new cycle begins.
- Test case: Repeatability.

**Answer button**

FR-07 — The screen must provide exactly one button labelled "Answer". *(User: has a single, named action to take.)*
- Pass: One button with the visible label "Answer" is present.
- Fail: The button is absent; the label differs from "Answer"; more than one button is present.
- Test case: Correct answer path, Wrong answer path, Empty field.

FR-08 — Pressing the Answer button must be the sole trigger for evaluation. No other user action — including pressing Enter or any keyboard shortcut — is required or implied. *(User: does not need to learn a secondary trigger.)*
- Pass: Evaluation fires only when the Answer button is pressed.
- Fail: Evaluation fires on any other event; pressing the button does not trigger evaluation.
- Test case: Correct answer path, Wrong answer path.

**Evaluation logic**

FR-09 — When the Answer button is pressed and the user's input, parsed as an integer, equals the sum of the two displayed numbers, the application must trigger celebration visuals and must not trigger sad dog visuals. *(User: receives the correct reward signal.)*
- Pass: Celebration plays; sad dog is absent.
- Fail: Sad dog plays; both play; neither plays; celebration plays for any other condition.
- Test case: Correct answer path, No wrong-condition feedback.

FR-10 — When the Answer button is pressed and the user's input does not equal the sum of the two displayed numbers, the application must trigger sad dog visuals and must not trigger celebration visuals. *(User: receives the correct commiseration signal.)*
- Pass: Sad dog plays; celebration is absent.
- Fail: Celebration plays; both play; neither plays; sad dog plays for any other condition.
- Test case: Wrong answer path, No wrong-condition feedback.

FR-11 — When the Answer button is pressed and the answer field is empty, the application must not crash or produce an error. The empty input must be treated as a wrong answer (sad dog plays) or the application must do nothing; it must not produce a blank or undefined state. *(User: is not punished with a broken screen for pressing the button too early.)*
- Pass: Application remains functional; either sad dog plays or nothing happens; no error is thrown.
- Fail: Application crashes; console error is produced; a blank or undefined visual state appears.
- Test case: Empty field, No console errors.

FR-12 — Input that cannot be parsed as a valid integer must be treated as a wrong answer. The application must not throw an uncaught exception for any typed input. *(User: cannot break the screen by typing letters or symbols.)*
- Pass: Non-numeric input results in sad dog or no response; no exception is thrown.
- Fail: An uncaught exception is thrown; the application enters an error state.
- Test case: Empty field, No console errors.

**Feedback visuals**

FR-13 — Celebration visuals must be animated, not a static image. *(User: receives a moment of joy, not a flat graphic.)*
- Pass: The celebration response involves visible motion or animation.
- Fail: The celebration response is a static image with no animation.
- Test case: Correct answer path.

FR-14 — Sad dog visuals must be animated, not a static image. *(User: receives a moment of commiseration, not a flat graphic.)*
- Pass: The sad dog response involves visible motion or animation.
- Fail: The sad dog response is a static image with no animation.
- Test case: Wrong answer path.

FR-15 — Feedback must be immediate: no perceptible delay between the Answer button press and the start of the visual response. *(User: connects the button press to the feedback without confusion.)*
- Pass: Visual response begins within one rendering frame of the button press; no blank interval is visible.
- Fail: A blank or frozen interval is visible between button press and feedback start.
- Test case: Correct answer path, Wrong answer path.

FR-16 — Only one feedback type may be visible at any time. Celebration and sad dog visuals must never appear simultaneously. *(User: receives an unambiguous signal.)*
- Pass: At any moment, at most one feedback type is visible.
- Fail: Both celebration and sad dog visuals are visible at the same time.
- Test case: No wrong-condition feedback.

**Repeatability and reset**

FR-17 — After feedback has played on either the correct or wrong path, the user must be able to complete another interaction cycle without reloading the page. *(User: can practise repeatedly.)*
- Pass: A new problem is presented and the answer field is ready after feedback; the user can press Answer again.
- Fail: The screen is stuck in a post-feedback state; a page reload is required to continue.
- Test case: Repeatability.

FR-18 — The reset sequence must place the application in a clean ready state: the answer field is cleared, the feedback layer is hidden, and two numbers are displayed (which may be the same numbers or newly generated numbers). *(User: sees a fresh problem, not residue from the previous cycle.)*
- Pass: After reset, the field is empty, no feedback is visible, and two numbers are shown.
- Fail: Any element of the previous cycle's state persists visibly into the next cycle.
- Test case: Repeatability.

FR-19 — The reset must be triggered without requiring any user action beyond what is natural to the flow (for example, a "Play again" button is acceptable; requiring a page reload is not). *(User: does not need to learn a manual reset procedure.)*
- Pass: The user can reach the ready state by a single, obvious action or automatically after feedback.
- Fail: The user must reload the page or take a non-obvious action to reset.
- Test case: Repeatability.

## Non-functional requirements

Performance, security, usability, compliance — targets, not adjectives.

NFR-01 — **Performance: feedback latency.** The visual response to a button press must begin within one rendering frame (approximately 16 ms at 60 fps) of the press event firing. No artificial delay is introduced.
- Pass: No blank interval is visible between button press and feedback start.
- Fail: A perceptible blank or frozen interval is visible.

NFR-02 — **Performance: load time.** The application must be fully interactive within two seconds of opening `index.html` in a current evergreen browser over a local file system. No network request is made at load.
- Pass: The screen is ready to use within two seconds; the browser console shows no network errors.
- Fail: The screen is not interactive after two seconds; a network request is attempted.

NFR-03 — **Reliability: no console errors.** The browser developer console must show zero errors and zero warnings at load and after any button press on any of the six named test cases.
- Pass: Console is clean across all six test cases.
- Fail: Any error or warning appears in the console under any test case.

NFR-04 — **Usability: no instruction required.** A user who has not read any documentation must be able to see the numbers, type an answer, press the button, and understand the response without guidance.
- Pass: A first-time user completes the interaction without confusion; all interactive elements are self-evident.
- Fail: Any element requires explanation before use.

NFR-05 — **Usability: single screen.** The entire experience must be contained on one screen. No scrolling to reach any interactive element is required on a standard desktop or tablet viewport.
- Pass: All four parts (number display, answer field, Answer button, feedback layer) are visible without scrolling.
- Fail: Any interactive element requires scrolling to reach.

NFR-06 — **Security and isolation: no external resources.** No script, stylesheet, font, image, or asset is loaded from a URL. All resources are local files. The application functions correctly with no network connection.
- Pass: The application loads and runs fully with network access disabled.
- Fail: Any resource fails to load when the network is unavailable; any CDN link is present in any file.

NFR-07 — **Compliance: no persistence.** No value is written to `localStorage`, `sessionStorage`, cookies, IndexedDB, or any other storage mechanism. All runtime state is held in JavaScript variables for the duration of one page session only.
- Pass: Inspecting browser storage after use shows no values written by this application.
- Fail: Any value is found in browser storage after use.

## Data requirements

What must be stored, kept, reported.

DR-01 — **Operand one.** The first displayed number. Stored as a JavaScript variable for the duration of one interaction cycle. Discarded or overwritten at reset. Never written to any persistent storage.

DR-02 — **Operand two.** The second displayed number. Stored as a JavaScript variable for the duration of one interaction cycle. Discarded or overwritten at reset. Never written to any persistent storage.

DR-03 — **Correct answer.** The sum of operand one and operand two. Derived at the time the numbers are set; stored as a JavaScript variable for the duration of one interaction cycle. Discarded or overwritten at reset. Never written to any persistent storage.

DR-04 — **User input.** The value typed into the answer field. Read from the DOM element's value property at the moment the Answer button is pressed. Not stored in a JavaScript variable beyond the evaluation call. Cleared from the DOM at reset.

DR-05 — **Feedback state.** Whether the feedback layer is currently showing celebration, sad dog, or nothing. Represented by CSS classes on the feedback layer element (`is-correct`, `is-wrong`, `is-hidden` or equivalent). Not stored as a separate JavaScript variable; the DOM is the source of truth for visual state. Cleared at reset.

DR-06 — **No other data.** No score, no attempt count, no history, no timestamp, and no user identifier is created, stored, or transmitted at any point.

## Out of scope

What was asked and is not done, with the reason.

OOS-01 — **Score tracking.** No running score, attempt count, or streak is displayed or stored. *Reason: the brief defines one interaction — answer and see — with no history. The overview explicitly excludes scoring.*

OOS-02 — **Multiple arithmetic operations.** Only addition is in scope. Subtraction, multiplication, division, and operator selection are excluded. *Reason: the Conductor confirmed addition as the sole operation; the overview states addition only.*

OOS-03 — **User-entered operands.** The user does not set either number. The application generates or sets both operands. *Reason: the overview assumption is that the application sets the numbers; the brief describes "two number inputs" as things the user responds to, not configures.*

OOS-04 — **More than two operands.** The problem is always expressed as exactly two numbers. *Reason: the overview constraint states two number inputs only.*

OOS-05 — **Timer or time pressure.** No countdown, time limit, or time-based scoring exists. *Reason: the overview assumption states there is no time constraint; the brief describes no timer.*

OOS-06 — **Difficulty levels or number ranges configurable by the user.** The user has no control over the range or difficulty of the numbers presented. *Reason: the brief and overview describe no configuration; adding it would widen scope.*

OOS-07 — **Partial credit or "close" feedback.** The response is binary: correct or wrong. No "nearly right" state exists. *Reason: the overview constraint states binary feedback only.*

OOS-08 — **Neutral or idle state feedback.** No feedback plays when the screen first loads or when no answer has been submitted. *Reason: the brief describes feedback only on button press; a neutral feedback state is not described.*

OOS-09 — **Keyboard-only or accessibility-standard compliance.** The application is not designed to any clinical or educational accessibility standard. *Reason: the vision explicitly excludes this; the brief does not name it.*

OOS-10 — **Multiple pages, routing, or navigation.** The application is a single screen. No second page, route, or view exists. *Reason: the overview constraint states single screen.*

OOS-11 — **External dependencies, frameworks, or libraries.** No npm package, CDN link, or third-party asset is introduced. *Reason: the instructions and principles require browser-native capabilities first; no role may introduce a dependency without raising to the Conductor.*

## Priorities

Must, should, could — and the rule for cutting.

**Must (delivery is not done without these)**

- FR-01 through FR-19: all functional requirements are must-have. The application has one interaction; every requirement describes a part of that interaction or its correctness guarantee. None can be deferred without breaking the product.
- NFR-01 (feedback latency), NFR-03 (no console errors), NFR-04 (no instruction required), NFR-06 (no external resources), NFR-07 (no persistence): these are correctness and integrity requirements, not enhancements.
- DR-01 through DR-06: the data requirements are the minimum necessary to make the interaction work and to confirm no persistence occurs.

**Should (strongly expected; a deliberate decision is needed to omit)**

- NFR-02 (load time under two seconds): the application is trivially small and this target will be met without effort, but it is listed as should rather than must because the load time is a consequence of the file size, not a separately engineered property.
- NFR-05 (single screen, no scrolling): layout is expected to fit a standard viewport, but the exact viewport size is not specified; a builder working on an unusually small screen may need to make a layout trade-off. This is should rather than must to allow that judgement without a raise.

**Could (desirable if cost is zero; dropped if any trade-off arises)**

- There are no could items. The scope is fixed and minimal. Any addition beyond what is listed above is out of scope and requires a Conductor decision before it is considered.

**Rule for cutting**

If a conflict arises between requirements during build, the ordered principles govern: Feedback is the product (FR-09, FR-10, FR-13, FR-14, FR-16 are never cut); One interaction, no friction (FR-07, FR-08, NFR-04 are never cut); Correct beats clever (NFR-01, NFR-03 beat any visual enhancement). A builder who believes a must requirement cannot be met raises to the Conductor rather than deciding alone which requirement to drop.
